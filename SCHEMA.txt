Database Schema (Authoritative)
Project: Anime Lighthouse Index

---

1. Source of Truth

This schema reflects the actual PostgreSQL database (Supabase).

It distinguishes between:
- Database-enforced constraints
- Application-level assumptions (NOT enforced)

---

2. Table: lighthouses

Purpose:
Reference table for real-world lighthouses.

Columns:

- id
  type: integer
  constraints: PRIMARY KEY, GENERATED ALWAYS AS IDENTITY, NOT NULL

- name_en
  type: text
  constraints: NULLABLE

- name_jp
  type: text
  constraints: NULLABLE

- wiki_en
  type: text
  constraints: NULLABLE

- wiki_jp
  type: text
  constraints: NULLABLE

- lighthouse_japan_link
  type: text
  constraints: NULLABLE

- google_maps_link
  type: text
  constraints: NULLABLE

- notes_l
  type: text
  constraints: NULLABLE

- prefecture
  type: text
  constraints: NULLABLE

---

3. Table: sightings

Purpose:
Core dataset representing lighthouse appearances in media.

Columns:

- id
  type: integer
  constraints: PRIMARY KEY, GENERATED ALWAYS AS IDENTITY, NOT NULL

- date_spotted
  type: date
  constraints: NOT NULL

- title_en
  type: text
  constraints: NULLABLE

- title_r
  type: text
  constraints: NULLABLE

- title_jp
  type: text
  constraints: NULLABLE

- media_id
  type: text
  constraints: NULLABLE

- anilist_link
  type: text
  constraints: NULLABLE

- episode
  type: text
  constraints: NULLABLE

- timestamp
  type: text
  constraints: NULLABLE

- lighthouse_id
  type: integer
  constraints:
    - NULLABLE
    - FOREIGN KEY → lighthouses.id

- image_link
  type: text[]
  constraints: NULLABLE

- lighthouse_type
  type: enum (sighting_type)
  constraints:
    - NOT NULL
    - DEFAULT 'fictional'

- media_type
  type: enum (media_type)
  constraints:
    - NOT NULL
    - DEFAULT 'anime'

- notes
  type: text
  constraints: NULLABLE

---

4. Enum Types

4.1 sighting_type

Allowed values:
- 'real'
- 'fictional'

---

4.2 media_type

Allowed values:
- 'anime'
- 'manga'

---

5. Relationships

- sightings.lighthouse_id → lighthouses.id

Cardinality:
- many sightings → one lighthouse

Behaviour:
- lighthouse_id may be NULL
- no conditional constraint based on lighthouse_type

---

6. Database-Enforced Constraints (STRICT)

The database guarantees:

- id is unique and auto-generated
- date_spotted is always present
- lighthouse_type is always present
- media_type is always present
- lighthouse_id (if not null) must reference a valid lighthouse

---

7. NOT Enforced by Database (CRITICAL)

The database DOES NOT enforce:

- presence of titles (title_en, title_r, title_jp)
- relationship between lighthouse_type and lighthouse_id
- validity of image_link format
- correctness of URLs
- consistency between media_type and anilist_link

---

8. Application-Level Invariants (EXPECTED BUT NOT ENFORCED)

These are required for correct behaviour but enforced in frontend:

- lighthouse_type logic:
  IF 'real'      → lighthouse_id MUST exist
  IF 'fictional' → lighthouse_id MUST be NULL

- titles:
  title_r MUST exist
  title_jp MUST exist
  title_en MUST exist (fallback to romaji if needed)

- image_link:
  must be null OR array of strings
  each string format: "images/<filename>"

---

9. API Representation Notes

Supabase returns joined data using:

select=*,lighthouses(*)

Result:

- "lighthouses" field:
  - object when relation exists
  - null or omitted when not

10. Design Philosophy

Current schema is:

- permissive
- flexible
- frontend-driven for validation

This supports rapid iteration but relies on valid input.
