Enhancements (backlog only)
===========================

Items here are not committed product promises — they are ideas and future work. Shipped
behaviour is documented in FEATURES.txt; product intent in PRD.txt.


1. Lite fallback site (separate repo)

Maintain a second GitHub Pages repo with a stripped-down copy of the site so readers
still get a usable index if maintainer tooling or luxury integrations break and cannot
be fixed quickly without support.

Scope for the lite repo:
- Browse only: Recent, List, About.
- No public submit, review queue, trace.moe, SauceNAO, ImageMagick processing, or
  other auth-gated maintainer pages.
- Read path should not depend on live Supabase at runtime: periodic export of sightings
  (and lighthouse join data as needed) to a committed JSON file that dataservice loads
  instead of the API. 
- Images also exported from Supabase and stored in repo.
- Deploy independently from animelighthouses.github.io so a bad deploy on main does not
  take down the fallback.

Maintenance model:
- Freeze lite scope; refresh data via an occasional export script, not by merging every
  main-branch feature.
- Cherry-pick or hand-port browse-only fixes when desired; do not port submit/admin
  complexity unless lite scope is deliberately expanded.
- One short recovery note for the maintainer (export → commit JSON → push lite repo).

See ARCHITECTURE.txt for which pages and modules belong to browse vs submit layers.


2. Bookmarkable pagination

Reflect browse page index in the URL (e.g. ?page=2 for page 2; page 0 omits query). Enables
sharing and browser back/forward alignment with paging.


3. Contact / feedback form

Lightweight public message table (text; optional name/contact). Anti-abuse measures; email
notifications to maintainer.


4. Optional media normalization

Dedicated media table keyed by AniList id — fewer repeated fetches; room for richer media
metadata. Evaluate friction for sightings without AniList linkage (fallback UX).


5. Schema split exploration (separate tables for anime vs manga sightings)

Separate tables to drop media_type ambiguity and optionally use chapter vs episode fields;
evaluate submit complexity and incomplete-metadata cases.

- Cons: submit button becomes more complex; relies on AniList url to determine which table it needs to be added to; would need to add media type dropdown to submit form for when anilist link isnt available (possibly fallback general url).


6. Line breaks in notes field

Allow submitters and maintainers to enter multi-line notes (paragraphs, lists) and have
those breaks preserved on sighting cards and detail views.

Current behaviour: textarea inputs accept newlines, but browse rendering
(js/browse/noteText.js) inserts plain text nodes — HTML collapses `\n` to a single space,
so cards show one long line unless CSS changes are added.

Possible approach:
- Render `\n` as `<br>` or use `white-space: pre-wrap` on `.notes` text (watch link parsing
  in noteText.js still works across line boundaries).
- Confirm public submit, review prefill, and edit save round-trip newlines unchanged in
  Postgres text columns.
- Decide whether single line breaks only, or also blank-line paragraph spacing.
